### B22. Every app had no network after the first 17k upgrade: Settings.Global `restricted_networking_mode` = 1 (found 2026-11-06 on 17k) — fixed LIVE, guard baked in 17k-r2; ROOT CAUSE (the writer) UNKNOWN
Evidence: after the first 17k upgrade the phone had `restricted_networking_mode` = 1. Every normal app had no network (Wi-Fi AND cellular) while the adb shell still did; `dumpsys netpolicy` showed "Restricted networking mode: true" and blocked_state RESTRICTED_MODE for app UIDs. The settings row had defaultValue=1 defaultSysSet=true (so created by a system component, not by the user or by us), was absent from the 2026-11-05 13:17 settings backup, and survived a reboot while it was 1.
Live workaround (worked immediately): `settings put global restricted_networking_mode 0`. After one more reboot the key reads null (unset, restricted mode false).
What is baked (17k-r2): `tools/live/netguard/port-netguard.sh` + `.rc` -> `/vendor/odm/bin/port-netguard.sh` (0755 vendor_file), `/vendor/odm/etc/init/port-netguard.rc` (0644 vendor_configs_file; init oneshot service `port_netguard`, user root, seclabel u:r:su:s0, started at `sys.boot_completed=1`). Logic: `settings get global restricted_networking_mode`; if exactly `1` -> `settings put global ... 0` and `log -t netguard`. Checks at start, +30 s, +120 s, +300 s, then the script exits. NO permanent loop (no periodic wakeups: idle drain is under investigation). null/0 -> nothing. Offline stub tests (WSL dash, stub settings/log/sleep): 1 then 0; null; 0; 1 that survives the put (re-tried at every check, exits after +300 s); value turning 1 only at +120 s (cleared). Installers (all four): after the final flash, non-fatal, bounded wait for adb+boot, then as the shell user `settings get global restricted_networking_mode`, and if 1 `settings put ... 0`.
What is NOT known: WHO writes the 1 (no script, doc or transcript of ours sets it; the investigation was cut short; candidates not checked: a framework/ColorOS component reacting to the upgrade first boot or to a data-saver/ROM-update flow, e.g. the netpolicy/connectivity "restricted networking mode" used for setup/guest states). The guard is therefore DEFENSIVE, not a root-cause fix: it only clears the value within ~5 minutes of boot (a writer that acts later is not covered), and the boot-time start from /odm was not tested on a phone. Next step if it recurs: `settings list global | grep restricted`, `dumpsys netpolicy`, logcat for `restricted_networking_mode` / `setRestrictedNetworkingMode`, `content query` of settings_global history to see the writer package.

### B20. Charging limit (Settings > Battery > charging limit, 85 %) never stopped charging (2026-11-04, on 17j-r2) — FIXED LIVE (reversible, lost on reboot), NOT baked, files staged in `tools/live/odm-services`
Root cause: Battery.apk (`x8/k`, regular charge protection) does not use `setCustomSelectChgMode`; it sends the limit as `OplusBatteryManager.setChgConfig(14, "2++<switch>+<level>")` to OplusBatteryService -> `ICharger.setChgConfig`, which the stock vendor charger HAL turns into a kernel cut-off. Our Java ICharger stand-in (`tools/live/charger-aidl`) implements `setChgConfig`/`getChgConfig` as no-ops (return 0 / ""; log "get getChgConfig wrong!"), so nothing enforced the limit. `setCustomSelectChgMode(4, b)` is only called by the thermal GuardElf control. Hardware DOES support cutting charge: `battery/mmi_charging_enable` 0 -> status Not charging/Discharging within 4 s (usb online stays 1, current ~0), 1 -> charges again (verified at 100 %); `input_suspend` stays 0.
Fix: `tools/live/chglimit/port-chglimit.sh` (+ `port-chglimit.rc`, init service `port_chglimit` at boot_completed, same pattern as port-colormode): while USB/AC is online it reads system settings `regular_charge_protection_switch_state` and `regular_charge_protection_open_power_level`; level >= limit -> `mmi_charging_enable=0`; releases (=1) when the switch is off, unplugged, the limit changes above the level, or level <= limit-2. Polls 20 s near the limit, else 60 s (only a `settings get` + sysfs reads). Live verified at level 100 / limit 85: hold within 20 s (Discharging), switch 0 -> released (Full), switch 1 -> held again; logcat tag `chglimit`.
Live: `/data/local/tmp/port-chglimit.sh` run with `setsid sh ... &`. Revert: `pkill -f port-chglimit; echo 1 > /sys/class/power_supply/battery/mmi_charging_enable`.
Bake: `tools/live/odm-services/install.list` + `SHA256SUMS` already list `port/bin/port-chglimit.sh` (d7606391...) -> `/vendor/odm/bin/port-chglimit.sh` (0755 vendor_file) and `port/etc/init/port-chglimit.rc` (72d396c8...) -> `/vendor/odm/etc/init/` (0644 vendor_configs_file); no kernel/sepolicy change (seclabel u:r:su:s0 like colormode). Not tested: unplug/replug, charging resume after the level falls, boot-time start (needs a build; wait for approval). Note: toggling `regular_charge_protection_status` by hand makes Battery.apk clear `switch_state`; set both back to 1.

### B2. 内存扩展 (nandswap) workaround
Finding: the ColorOS "memory extension" page sets `persist.sys.oplus.nandswap` (switch) and `persist.sys.oplus.nandswap.swapsize` (4 / 6 / 8 GB; cfg `4,6,8`). The stock `/product/bin/init.oplus.nandswap.sh` needs ColorOS kernel hooks
(`/sys/block/zram0/hybridswap_*`, memcg `memory.swapd_*`, `/proc/nandswap/fn_enable`, `CONFIG_ZRAM_WRITEBACK`), none of which exist in this LineageOS kernel, so it records `persist.sys.oplus.nandswap.err=1004`, the page turns itself off, and only the 1.5 GB zram is active.
Workaround `tools/live/nandswap/port-nandswap.sh [GB|off]` (reads the two props by default; idempotent): swap file `/data/nandswap/swapfile` (`/data` is ext4, so no pinning), `fallocate -l NG -o 0`, `losetup -f -s`, `/product/bin/nandswap_tool -l <loop>` (direct I/O), `mkswap`, `swapon` WITHOUT `-p` (toybox rejects negative priorities; the kernel assigns -3, below zram -2), sets `swapsize.curr` and `err=0`.
Gotchas found: Android `sh` arithmetic is 32-bit (compute bytes in awk, pass `NG` to fallocate); keep LF line endings; free-space guard 15 %.
Live-verified: 4 GB active at -3, resize 4 → 6 GB, off. A live 5-second polling watcher is running (setsid loop) so the page choices apply; stock script races it at boot (it rewrites err 1004 at post-fs-data).
How to bake: ship the script (e.g. `/system/bin/port-nandswap.sh`), rc: `on property:persist.sys.oplus.nandswap=*`, `on property:persist.sys.oplus.nandswap.swapsize=*` and `on property:sys.boot_completed=1` each `exec_background u:r:su:s0 root root -- /system/bin/sh -c "sleep 5; /system/bin/port-nandswap.sh"` (swap does not survive reboot).
